插件权限与角色分配

插件怎么声明“可以分给角色”的权限，装插件时怎么给五个内置角色默认分配、由谁确认，授权者能把这些权限分给谁，插件停用、卸载、升级时这些授权怎么处理。本文只是方案，不改代码，也不发布。

结论

现有体系已经做了大半：清单里的 userPermissions 可以写名称、说明、敏感标记、默认角色和改名继承；安装确认页能逐个权限改分给哪些角色；升级只给新增的权限套默认值；停用时授权保留。还差的部分，推荐这样补：

  1. 先分清两类：插件自己申请的访问权限（hostPermissions，已有，不改），和插件声明给用户的权限（userPermissions，本方案的重点）。两类都在安装确认页、插件设置页“权限”标签、角色编辑页三处配置。
  2. 声明补四个字段：group 分组、risk 三级风险、requires 依赖、scope 范围。权限 key 仍是 资源:动作，范围不写进 key，在授权时选，存成 key 末尾一段（如 :flow/3）。这和核心账号权限的 :own、:group/12 是同一套规则。
  3. 通配 a:* 只在勾选时用，不存进数据库：保存时展开成当时的具体 key。插件以后升级新增的权限，不会被通配悄悄带进任何角色。
  4. 默认分配按内置角色写建议，安装确认页用一张“权限 × 角色”表审阅修改。安装者无权分配的角色，不直接按清单授予，挂起等超级管理员复核。
  5. 防提权沿用现有规则，插件权限没有特例：授出的权限不超过自己拥有的，改动的角色必须在自己的“可分配角色”清单里。“管理员能授权哪些角色”由角色本身的可分配清单表达，插件不声明，也不能改这一点。
  6. 升级时删掉的权限改为“已移除”，授权保留但不生效，以后版本重新声明时带着原授权恢复，不重新套默认值。这样“撤销过的不被加回”在各种情况下都成立。
  7. 停用保留授权、卸载删除授权，保持现状。

两类权限，三个配置入口

① 插件申请的权限（访问资源）

插件自己要用系统资源，比如读用户、写库、访问外网、记账。清单 hostPermissions 已有，带风险等级和可收窄的范围。授权对象是插件本身，安装时由管理员批准，高风险要 plugin:grant:high，关键要超管。本方案不改这部分。

② 插件声明给用户的权限

插件提供的功能，谁能用、能管到哪些数据，比如“编辑审核流程”“导出审核记录”。清单 userPermissions，授权对象是角色，进而是用户。本方案主要讲这一类。

两类权限在三个地方配置，用同一套组件：安装 / 首次启用时的确认页（按插件建议预填，管理员确认后插件立即拿到①，各角色立即拿到②）；插件设置页的“权限”标签（随时查看和修改这个插件的①和②，原型 D）；角色编辑页（按角色查看和修改，原型 C）。插件设置页和角色编辑页改的是同一份数据，从插件看或从角色看都行。

1. 现状盘点

读的代码：sdk/manifest（UserPermission）、server/internal/perm（key 与范围解析）、authz（目录、内置角色、可分配清单、CanGrant/CanGrantToRoles）、plugin/install（安装确认、升级授权、待复核）、前端 ConsentView 与 RolesView。

方面现在怎么做缺口
声明清单 userPermissions[]：key、label、description、sensitive、defaultRoles（不写时给 admin）、inheritFrom（改名继承）。核心把它登记为 plugin.<插件>:<key>，模块 plugin.<插件>。没有分组、依赖；风险只有“敏感/不敏感”
key 与范围本地 key 正则 ^[a-z0-9_]+(:[a-z0-9_]+)+$，只能是不带范围的整键。范围（*、own、group/12、account/125）只开放给核心账号、代理的 8 个动作，写死在 perm.scopable。插件权限不能限定到“某几个流程”“自己创建的”
安装确认每个新权限可改分给哪些角色（new_permission_roles）。只能选自己可分配清单里、且自己不持有的角色，需要 role:define。清单默认角色不做这项检查，照样授予
升级只对目录里还没有的 key 套默认；不敏感且只给内置 admin/operator/supplier 的自动通过，其余要确认；内置插件随核心升级时把要确认的挂起待复核。已有 key 不动，撤销的不会回来
升级删掉 keySyncPlugin 直接 DELETE 权限行，角色授权级联删除。之后版本再声明时当新 key，默认值重新套上，撤销过的会被加回
停用 / 启用权限行 status 改 disabled / active，角色授权保留，停用期间不生效。合理
卸载删除插件全部权限，角色授权级联删除。合理
防提权改角色权限要 ⊆ 自己的授予集（访问密钥会再收窄）；改内置角色或有人持有的角色，还要该角色在自己的可分配清单里。插件 key 是普通 key，同样适用。规则统一，可直接复用

2. 插件怎么声明权限

你提到的 a:b:c、a:*、a:own 和“多选”，其实是三件不同的事，处理方法也不同：

写法含义方案
flow:read、flow:manage一个具体动作插件在清单里逐个声明，路由和菜单按它判断。层级只用于命名和分组，不参与匹配。
flow:*、*一组动作只在角色编辑页和安装确认页作为“整组勾选”的快捷方式。保存时展开成当时存在的具体 key，数据库不存通配（见决策 D1）。
flow:manage:own、flow:manage:flow/3同一动作，只能作用在部分数据上清单给这个权限声明 scope，授权时选范围，存成 key 末尾一段。匹配规则沿用核心 perm.Implies：* 包含一切，own 只包含 own，flow/3 只包含它自己。
多选同一动作选多个范围值一个值存一行授权。核心 role_permission_scopes 已支持同一动作多行，角色编辑页的范围选择器 ScopePicker 也已支持多选，直接复用。

字段

字段状态说明
key已有<资源>:<动作>，不带插件前缀，不带范围。末段不能是 *、own 或含 /（留给范围）。
label / description已有中英文名称和说明，角色编辑页悬停显示。
group新增指向清单顶层 permissionGroups[] 的 key（带名称、排序）。角色编辑页按“插件 → 分组 → 权限”三层显示。
risk新增，取代 sensitivelow（默认）、sensitive（钱、凭证、用户原文、封禁等）、critical（能绕过安全控制，比如免审核）。critical 对应核心的“超管专属”：不能写进任何默认值，安装时只有超级管理员能勾（见决策 D3）。
requires新增弱依赖，比如“编辑”依赖“查看”。和核心 corePerm.requires 一样，只用来在勾选时提示，不影响鉴权。只能引用本插件的 key。
scope新增范围来源三选一：
· {"resource":"flow","options":"/scopes/flow","own":true}：插件自己的数据，候选值由插件的 options 路由提供，own 表示可选“自己创建的”；
· {"values":[{"key":"input","label":…}, …]}：固定枚举，候选值写在清单里；
· 核心资源（账号、分组、代理）不在插件 key 上做范围，改用路由已有的 accounts 声明，与核心 account:* 的范围取交集（见决策 D4）。
defaults新增，取代 defaultRoles给内置角色的建议。键是 admin、operator、supplier、user；值为 true（不带范围的权限），或范围数组如 ["*"]、["own"]。超级管理员不写，它永远拥有全部权限。没写的角色就是不给。
inheritFrom已有改名或拆分时继承旧 key 的持有者（带范围的继承原范围）。

示例（以提示词审核插件为例，假设的 1.0 版）

"permissionGroups": [
  { "key": "flow",   "label": { "zh": "审核流程", "en": "Flows" } },
  { "key": "record", "label": { "zh": "审核记录", "en": "Records" } },
  { "key": "action", "label": { "zh": "处置",     "en": "Actions" } }
],
"userPermissions": [
  { "key": "flow:read", "group": "flow", "label": { "zh": "查看审核流程" },
    "defaults": { "admin": true, "operator": true } },
  { "key": "flow:manage", "group": "flow", "risk": "sensitive", "requires": ["flow:read"],
    "scope": { "resource": "flow", "options": "/scopes/flow", "own": true },
    "defaults": { "admin": ["*"] } },
  { "key": "record:read", "group": "record",
    "scope": { "resource": "flow", "options": "/scopes/flow" },
    "defaults": { "admin": ["*"], "operator": ["*"] } },
  { "key": "record:export", "group": "record", "risk": "sensitive", "defaults": { "admin": true } },
  { "key": "exempt", "group": "action", "risk": "critical" }   // critical 不允许写 defaults
],
"routes": [
  { "method": "PUT", "path": "/flows/:id", "scope": "admin", "permission": "flow:manage",

]

运行时谁来判断

路由写 permission 加 scopeFrom（取值来源：path:、query:、body:，和 accounts.from 同一种写法），核心在转发前判断范围，插件不用自己判断。列表类接口需要“调用者能看哪些流程”，就扩展现有的 AuthzCheck：返回该动作的范围列表（all、own、ids），插件据此过滤。

“自己创建的”怎么判断

核心不知道插件数据的创建者，所以 own 由插件判断：核心在请求里带上“该动作只有 own 范围”，插件按自己表里的 created_by 过滤。核心账号已有的 own 规则不受影响。

清单校验（manifest check）

分组必须存在；requires、inheritFrom 只能引用本插件的 key；critical 不能写 defaults；defaults 的范围必须是 scope 允许的值；不能同时写 sensitive 和 risk。用了新字段的清单 UI 下限升到 3.16，旧核心拒绝安装。

3. 默认分配、确认和之后的修改

安装或首次启用：确认页的“插件权限”一节改成一张“权限 × 角色”表，初值就是清单 defaults。规则如下：

  • 超级管理员一列固定全勾、不能改。自定义角色默认收起，点“更多角色”展开。
  • 改过的格子标“已改”，每行和整表都有“恢复插件建议”。
  • 敏感 行照常按建议预勾，但底部汇总会写明“将把 N 项敏感权限授予 M 个角色”。关键 行全部不勾，只有超级管理员能勾。
  • 安装者无权分配的角色（不在自己的可分配清单里，或是自己持有的角色），格子置灰并标“待超管复核”。这些建议不直接授予，进入现有的“待复核授权”队列，超级管理员在插件详情里确认或拒绝。现有的 withholdGrants 和 PendingRoleGrants 可以直接复用。

下面的原型可以切换查看身份。用“管理员”身份看时，“管理员”一列整列置灰：默认可分配清单里没有 admin 自己，按现有规则管理员也不能给自己持有的角色加插件权限。

4. 谁能把插件权限授给谁

全系统只有一条规则，插件权限不开特例：

  • 授出的不超过自己拥有的：角色编辑页保存时，新增的 key（含范围）必须被自己的授予集包含（covers / perm.Implies）。插件资源范围按同一规则比较：有 flow:manage（全部）的人可以授出 flow:manage:flow/3，反过来不行。
  • 只能动自己可分配的角色：改内置角色或有人持有的角色，要求该角色在自己的可分配清单里（editableRole）。

唯一需要额外规则的时刻是安装或升级时创建新权限。那一刻新权限还没有任何人持有，“不超过自己”无从比较，所以现有代码换成：目标角色在安装者的可分配清单里，并且不是安装者自己持有的角色（pluginGrantee），超级管理员不受限。本方案只补两点：关键 权限只有超级管理员能分；清单默认值也走这条检查，过不了的挂起复核（决策 D2）。

“管理员可以授权哪些角色”不需要插件参与。这已经由每个角色的可分配清单表达（role_assignable_roles 加“所有自定义角色”开关），默认是：

授权者角色可分配角色（默认）能给哪些角色分插件权限
超级管理员全部（除超管自身，超管只能移交）全部角色，含关键权限。安装时“管理员”一列只有它能勾。
管理员运维、供应商、普通用户、所有自定义角色这些角色，且只能分自己拥有的；管理员自己这一列由超管复核。
运维供应商、普通用户同上。默认没有 role:define，所以实际不能改角色权限，只能分配角色。
自定义角色按角色配置按角色配置。

插件不能声明“哪些人可以授权我的权限”，理由有两点：第一，这样插件就能决定站内的授权结构，越界了；第二，风险等级已经足够表达“这个权限要更高级别的人来分”。参考两个常见做法：

Kubernetes RBAC

靠 escalate 和 bind 两个动词防提权：没有 escalate 就只能授出自己已有的权限，没有 bind 就只能绑定自己已有权限的角色，对应我们的“不超过自己”和“可分配清单”。它的聚合 ClusterRole 按标签自动并入新规则，相当于活动通配，会让新增权限自动扩散，这正是决策 D1 推荐不做的。

Grafana 插件 RBAC

插件在 plugin.json 里声明角色和动作（动作名 <插件id>.<资源>:<动作>，范围如 folders:uid:abc），并用 grants 指定默认给 Viewer、Editor、Admin 哪些基础角色，管理员之后可以改。我们的 defaults 就是这个思路，再加上安装时人工审阅和可分配清单检查。

5. 停用、卸载、升级删除时授权的去留

事件权限条目角色授权访问密钥里的这个 key
停用插件disabled（现状）保留，不生效；角色页置灰显示保留，不生效
重新启用active（现状）原样恢复，不再弹确认恢复
升级时某 key 不再声明removed（新，现在是直接删除）保留，不生效；角色页显示“已移除”，只能取消勾选保留，不生效
之后版本重新声明active带着原授权恢复，不重新套默认值恢复
卸载删除（现状）删除不再匹配任何权限，等于没有；访问密钥总是和用户角色取交集，不会越权
卸载后重装新建按安装确认页重新确认—

“removed”这个状态核心权限已经在用（SyncCore 把代码里删掉的核心权限标 removed，writeGrants 保留其授权，key 回来时原样复活）。插件权限改用同一状态，SyncPlugin 里把 DELETE 换成 UPDATE … SET status = 'removed' 就行，改动很小。

6. 需要你定的选项

D1通配 a:* 怎么存推荐：只作勾选快捷方式，保存时展开成具体 key另一个选择是存成活动通配、跟着升级自动包含新权限。那样新权限会绕过升级确认，敏感权限也会悄悄扩散，防提权比较也要处理通配对通配，不推荐。
D2清单默认值给了安装者无权分配的角色推荐：挂起，等超级管理员复核另一个选择是保持现状，按清单直接授予。生产上目前只有超级管理员安装插件，两种做法实际效果一样；区别在以后有了管理员账号时，管理员装插件能不能借插件默认值给自己的角色加权限。
D3风险等级推荐：low / sensitive / critical 三级，critical 等同“超管专属”另一个选择是保留 sensitive 布尔值。“免审核”这类能绕过安全控制的权限就无法和普通敏感权限区分。
D4插件操作账号时的范围推荐：插件 key 不带账号范围，路由用 accounts 声明，与核心 account:* 的范围取交集例如 Codex 的“重置次数”：供应商有 plugin.codex:reset 加核心 account:update:own，就只能重置自己的账号。另一个选择是插件 key 也能写 :own、:group/12，但那就有两套账号范围，配置时容易冲突。
D5卸载后重装推荐：清空重来，重新走安装确认页另一个选择是保留授权记录，重装后恢复。卸载本来就会删插件数据，保留授权反而容易让人意外。
D6升级时删掉的 key推荐：标 removed，保留授权不生效另一个选择是保持现状直接删除，但之后版本重新声明时撤销过的授权会被默认值加回，和“不覆盖已撤销”冲突。

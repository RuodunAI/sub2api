# 0.1.289 插件权限声明的回滚

> 版本号 0.1.289 随 `manifest.PluginPermissionsFirstCore`，是推测值，发布时改成真实版本（文件名、脚本里的 `via` 与本文一起改）。

核心 0.1.289 只有一个新迁移 `0099_plugin_permission_meta.sql`（设计见 `docs/plugin-permissions/02-authz.md` §2.3.2）：给 `permissions` 加 `risk`、`requires`、`group_key`、`group_label`、`group_sort`、`scope`、`defaults` 七列与约束 `permissions_risk_check`，`scope_type` 加宽到 `varchar(40)`；`sensitive` 列保留，新核心照写（`risk <> 'low'`）。回滚目标是上一版本核心 0.1.288（schema 0098）。

旧核心在新库上的问题不在新列（它不读），而在新核心写出的两类数据：

- **已移除的插件权限**（`source = 'plugin' AND status = 'removed'`）：新核心对插件不再声明的 key 只标 removed、授予保留；0.1.288 的 `SetPluginActive` 会把整个插件的权限行改回 active/disabled，这些授予重新生效。
- **插件范围授予**（`role_permission_scopes` 里属于插件权限的行，如 `plugin.m:flow:manage:flow/3`）：0.1.288 的 `perm` 解析不了，本来就不起作用。

托管核心见到库里有它不认识的迁移会拒绝启动（`app/managed_checks.go` `appliedPrefix`），非托管核心照常启动。

**托管部署（线上网关）不能经升级计划回到 0.1.288。** 与 0.1.286 相同（见 `0.1.286-authz-down.md`）：网关不允许跨 schema 回退（`deploy/gateway/README.md`），建计划、主节点启动目标核心、`sub2api-gateway rollback` 三处都会拒绝；新版本内置插件的 `hostCompat` 是 `>=0.1.289`，计划预检也会拦下。线上出问题首选**修复前进**（下一个核心版本，新迁移接在 0099 之后），确实要回到 0.1.288 只能从数据库备份恢复。下面的步骤只适用于非托管部署（测试环境、生产备份验证环境、不经网关直接运行核心的部署）。

## 先判断要不要跑反向脚本

```sql
SELECT id FROM schema_migrations WHERE id = '0099_plugin_permission_meta.sql';
```

没有这一行说明迁移没有提交，库还是 0.1.288 的形态，不要跑反向脚本。

## 发布前记下

```sql
SELECT key, active_version FROM plugins ORDER BY key;
```

回滚时要把本次升级过的插件切回这些版本。

## 回滚步骤

1. **停掉所有 0.1.289 核心**。0.1.288 核心要在脚本跑完后再启动。
2. **跑反向脚本**（数据库属主，一个事务，失败不留半截）：

   ```sh
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.289-plugin-perm-down.sql
   ```

   脚本先检查 `0099_plugin_permission_meta.sql` 已应用、之后没有更新的迁移，否则直接报错退出、什么也不改。
3. **启动 0.1.288 核心**。库里的迁移正好是它的 0001–0098，不再跑迁移；它的权限同步按旧代码重写核心权限的 `sensitive`。
4. **插件切回发布前的版本**：声明了 `userPermissions` 的内置插件新版本 `hostCompat` 是 `>=0.1.289`，在 0.1.288 上启动失败。用超管会话对第 0 步记下的每个本次升级过的插件调用 `POST /api/v1/plugins/:key/upgrade {"version": "<发布前的版本>"}`。插件旧版本启动时 0.1.288 的同步按旧清单重写它的权限（新版本多出的 key 被删除，授予随之删除）。
5. **核对**：

   ```sql
   SELECT count(*) FROM schema_migrations WHERE id >= '0099';                                  -- 0
   SELECT column_name FROM information_schema.columns WHERE table_name = 'permissions'
   AND column_name IN ('risk', 'requires', 'group_key', 'group_label', 'group_sort', 'scope', 'defaults'); -- 无行
   SELECT count(*) FROM permissions WHERE source = 'plugin' AND status = 'removed';             -- 0
   SELECT target_id, detail->>'dropped' FROM audit_logs WHERE detail->>'via' = 'rollback 0.1.289';
   ```

## 脚本改回了什么

| 0.1.289 的状态 | 回滚后 | 依据 |
|---|---|---|
| 已移除的插件权限行及其授予（含范围授予） | 删除，每条授予写一条 `dropped` 审计 | 0.1.288 会复活它们；删除也是 0.1.288 对不再声明的 key 的做法 |
| 插件权限的范围授予 | 删除，每条写一条 `dropped` 审计 | 0.1.288 解析不了插件范围 |
| 插件权限行的 `scope_type` | 置 `''` | 0.1.288 不给插件权限范围类型，且列要改回 `varchar(20)` |
| `permissions` 的 7 个新列、`permissions_risk_check`、`status` 列注释 | 删除 | — |
| `permissions.scope_type varchar(40)` | `varchar(20)` | — |
| `schema_migrations` 的 `0099_plugin_permission_meta.sql` | 删除 | — |

审计都是系统操作者（`user_id` 为空）的 `authz.grant.migrate`，`detail = {"via": "rollback 0.1.289", "dropped": "<key>[:<scope>]"}`，`target_id` 是角色 id；最后推进 authz 版本。

## 回滚后的已知差异

- **已移除权限的保留授予丢失**：0.1.289 对插件不再声明的 key 保留授予、重新声明时原样复活；回滚把它们删掉，等同 0.1.288 的“删除”语义。审计里有原值，再次升级后插件重新声明这些 key 时它们按新建处理（套插件建议），需要原样恢复的照审计手工补回。
- **插件范围授予不保留**：同上，审计里有原值。
- **风险、分组、依赖、建议授予不保留**：都来自清单，再次升级后插件同步时重新写入。核心权限的 `risk` 由再次升级时迁移按 `sensitive` 回填，下次核心同步按代码改正（超管专属的为 critical）。

## 再次升级

直接再发 0.1.289。迁移重新加列并按 `sensitive` 回填 `risk`；核心与插件同步重新写入风险、分组、依赖、范围与建议授予。

`TestPluginPermissionMetaRollback`（`server/internal/migrations`）在测试库上验证：迁移到 0099 后造已移除插件权限与插件范围授予，执行本脚本后表结构与只迁移到 0098 的库一致，已移除行与插件范围授予被删除并逐条审计，核心范围授予与其他插件权限保留，再执行一次报 `nothing to roll back`，再升级成功。

# 0099 插件权限声明的回滚（只用于开发库、测试库）

> **线上不用这个脚本。** 插件权限声明随 0.1.290 发布（0099–0101 一起，见 `0.1.290-release.md`），0.1.289 没有单独发布；线上从 0.1.288 直接升级，回退只能从升级前的备份恢复。本文只适用于停在 0099 的库：跑过 develop 上编号为 0.1.289 的构建的开发库、测试库、生产备份验证环境。文件名和审计里的 `via: "rollback 0.1.289"` 沿用那个开发版本号：迁移 0099 的注释引用了这个文件名，0099 的字节不能再改。

develop 的 0.1.289 构建只有一个新迁移 `0099_plugin_permission_meta.sql`（设计见 `docs/plugin-permissions/02-authz.md` §2.3.2）：给 `permissions` 加 `risk`、`requires`、`group_key`、`group_label`、`group_sort`、`scope`、`defaults` 七列与约束 `permissions_risk_check`，`scope_type` 加宽到 `varchar(40)`；`sensitive` 列保留，新核心照写（`risk <> 'low'`）。回滚目标是上一版本核心 0.1.288（schema 0098）。

旧核心在新库上的问题不在新列（它不读），而在新核心写出的两类数据：

- **已移除的插件权限**（`source = 'plugin' AND status = 'removed'`）：新核心对插件不再声明的 key 只标 removed、授予保留；0.1.288 的 `SetPluginActive` 会把整个插件的权限行改回 active/disabled，这些授予重新生效。**暂存的插件权限**（`status = 'staged'`，只有已同意、尚未激活的版本声明的 key）同理会被 0.1.288 打开。
- **插件范围授予**（`role_permission_scopes` 里属于插件权限的行，如 `plugin.m:flow:manage:flow/3`）：0.1.288 的 `perm` 解析不了，本来就不起作用。
- **带范围或 critical 的待复核授予**（`plugin.consent.auto` 审计 `detail.pending` 里的元素，新核心写成 `{permission, role, scope, risk, …}`）：0.1.288 的复核列表只按 `permission/role` 读，不认识 `scope` 和 `risk`。确认一条 `flow/3` 范围的待复核项会变成整行授予；它也没有 critical 档，持有授予权的非超管就能确认 critical 项。

托管核心见到库里有它不认识的迁移会拒绝启动（`app/managed_checks.go` `appliedPrefix`），非托管核心照常启动。

**托管部署不能经升级计划回到 0.1.288。** 与 0.1.286 相同（见 `0.1.286-authz-down.md`）：网关不允许跨 schema 回退（`deploy/gateway/README.md`），建计划、主节点启动目标核心、`sub2api-gateway rollback` 三处都会拒绝。下面的步骤只适用于不经网关直接运行核心的开发库、测试库。

## 先判断要不要跑反向脚本

```sql
SELECT id FROM schema_migrations WHERE id = '0099_plugin_permission_meta.sql';
```

没有这一行说明迁移没有提交，库还是 0.1.288 的形态，不要跑反向脚本。

## 发布前记下

```sql
SELECT key, active_version FROM plugins ORDER BY key;
```

回滚时要把本次升级过的插件切回这些版本。

## 回滚步骤

1. **停掉所有 0.1.289 开发构建的核心**。0.1.288 核心要在脚本跑完后再启动。
2. **跑反向脚本**（数据库属主，一个事务，失败不留半截）：

   ```sh
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.289-plugin-perm-down.sql
   ```

   脚本先检查 `0099_plugin_permission_meta.sql` 已应用、之后没有更新的迁移，否则直接报错退出、什么也不改。
3. **启动 0.1.288 核心**。库里的迁移正好是它的 0001–0098，不再跑迁移；它的权限同步按旧代码重写核心权限的 `sensitive`。
4. **插件切回发布前的版本**：声明了 `userPermissions` 的内置插件新版本要求更新的核心（develop 上是 `>=0.1.289`，0.1.290 发布的版本是 `>=0.1.290`），在 0.1.288 上启动失败。用超管会话对第 0 步记下的每个本次升级过的插件调用 `POST /api/v1/plugins/:key/upgrade {"version": "<发布前的版本>"}`。插件旧版本启动时 0.1.288 的同步按旧清单重写它的权限（新版本多出的 key 被删除，授予随之删除）。
5. **核对**：

   ```sql
   SELECT count(*) FROM schema_migrations WHERE id >= '0099';                                  -- 0
   SELECT column_name FROM information_schema.columns WHERE table_name = 'permissions'
   AND column_name IN ('risk', 'requires', 'group_key', 'group_label', 'group_sort', 'scope', 'defaults'); -- 无行
   SELECT count(*) FROM permissions WHERE source = 'plugin' AND status IN ('removed', 'staged'); -- 0
   SELECT target_id, detail->>'dropped' FROM audit_logs WHERE action = 'authz.grant.migrate' AND detail->>'via' = 'rollback 0.1.289';
   SELECT target_id, detail->'grants' FROM audit_logs WHERE action = 'plugin.role_grants.reject' AND detail->>'via' = 'rollback 0.1.289';
   ```

## 脚本改回了什么

| 0.1.289 的状态 | 回滚后 | 依据 |
|---|---|---|
| 仍待复核的带范围或 critical 的授予（`plugin.consent.auto` 的 `pending`，已移除权限的除外） | 每个插件写一条拒绝审计 `plugin.role_grants.reject`，两版核心都不再列出 | 0.1.288 会把范围项确认成整行授予、让非超管确认 critical 项 |
| 已移除、暂存的插件权限行及其授予（含范围授予） | 删除，每条授予写一条 `dropped` 审计 | 0.1.288 会复活或打开它们；删除也是 0.1.288 对不再声明的 key 的做法；暂存版本回滚后要重新上传、同意 |
| 插件权限的范围授予 | 删除，每条写一条 `dropped` 审计 | 0.1.288 解析不了插件范围 |
| 插件权限行的 `scope_type` | 置 `''` | 0.1.288 不给插件权限范围类型，且列要改回 `varchar(20)` |
| `permissions` 的 7 个新列、`permissions_risk_check`、`status` 列注释 | 删除 | — |
| `permissions.scope_type varchar(40)` | `varchar(20)` | — |
| `schema_migrations` 的 `0099_plugin_permission_meta.sql` | 删除 | — |

审计都是系统操作者（`user_id` 为空）写的：删除的授予是 `authz.grant.migrate`，`detail = {"via": "rollback 0.1.289", "dropped": "<key>[:<scope>]"}`，`target_id` 是角色 id；拒绝的待复核授予是 `plugin.role_grants.reject`，`detail = {"via": "rollback 0.1.289", "grants": [{permission, role, scope, risk}]}`，`target_id` 是插件 key。最后推进 authz 版本。

## 回滚后的已知差异

- **已移除权限的保留授予丢失**：0.1.289 对插件不再声明的 key 保留授予、重新声明时原样复活；回滚把它们删掉，等同 0.1.288 的“删除”语义。审计里有原值，再次升级后插件重新声明这些 key 时它们按新建处理（套插件建议），需要原样恢复的照审计手工补回。
- **插件范围授予不保留**：同上，审计里有原值。
- **带范围或 critical 的待复核授予被拒绝**：拒绝按 0.1.288 和 0.1.289 共同的规则生效，即清掉此前各版本里同一个（权限，角色）的待复核项。所以同一对上整行的待复核项也一起清掉。再次升级后这些项也不会回来。需要的授予，在 0.1.289 上由超管在角色页或插件权限矩阵里手工授予。回滚前可以用下面的 SQL 列出会被拒绝的项，也可以先在 0.1.289 上逐个确认或拒绝：

  ```sql
  SELECT a.target_id, a.detail->>'version', g->>'permission', g->>'role', g->>'scope', p.risk
  FROM audit_logs a CROSS JOIN LATERAL jsonb_array_elements(a.detail->'pending') g
  JOIN permissions p ON p.key = g->>'permission' AND p.status <> 'removed'
  WHERE a.action = 'plugin.consent.auto' AND jsonb_typeof(a.detail->'pending') = 'array'
    AND (COALESCE(g->>'scope', '') <> '' OR p.risk = 'critical');   -- 含已处理过的，以 GET /api/v1/plugins/:key 的待复核列表为准
  ```

- **操作者同意时挂起的授予与改名继承的待复核项在 0.1.288 上看不到**：0.1.289 把操作者同意时不可命名角色的授予（D2）记在 `plugin.consent` 审计的 `detail.pending` 里，激活暂存升级时把改名旧 key 在同意之后新增的持有者记在 `plugin.role_grants.carry` 审计的 `detail.pending` 里，而 0.1.288 的复核列表只读 `plugin.consent.auto`。这些授予不会被授出，再次升级后重新出现在复核列表里。
- **风险、分组、依赖、建议授予不保留**：都来自清单，再次升级后插件同步时重新写入。核心权限的 `risk` 由再次升级时迁移按 `sensitive` 回填，下次核心同步按代码改正（超管专属的为 critical）。

## 再次升级

升级到 0.1.290（`0.1.290-release.md`）。0099 重新加列并按 `sensitive` 回填 `risk`，0100、0101 接着执行；核心与插件同步重新写入风险、分组、依赖、范围与建议授予。

`TestPluginPermissionMetaRollback`（`server/internal/migrations`）在测试库上验证：迁移到 0099 后造已移除插件权限与插件范围授予，执行本脚本后表结构与只迁移到 0098 的库一致，已移除行与插件范围授予被删除并逐条审计，仍待复核的范围项和 critical 项被拒绝（已复核的、整行非 critical 的不动），核心范围授予与其他插件权限保留，再执行一次报 `nothing to roll back`，再升级成功。

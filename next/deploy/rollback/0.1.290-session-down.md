# 0.1.290 控制台会话（Valkey `s2s_` 令牌）：单向发布

> 版本号 0.1.290 是候选值，发布时改成真实版本（文件名与本文、迁移 0101 的注释一起改）。

从本版本起，控制台登录只签发 `s2s_` 会话令牌，会话存放在 Valkey（设计见 CONTRACTS §100）。JWT 的签发与校验、`POST /auth/refresh`、开关 `session.issue`（`/settings/session`、`SUB2API_SESSION_ISSUE`）都已删除。迁移 `0101_drop_jwt_sessions.sql` 删除 `refresh_tokens`、`login_sessions`、`auth_flows` 三张表和设置行 `session`。

**这是单向发布：没有反向脚本，回到上一版只能从数据库备份恢复。**

## 发布的影响

- **所有人重新登录。** 上一版签发的 JWT 与刷新令牌全部失效：控制台下一次请求得到 401，直接回到登录页。访问密钥（`sak_`）不受影响。
- **Valkey 是登录的前提。** 会话、两步登录与二次验证的流程都只在 Valkey；Valkey 不可用时登录与控制台请求返回 503（不是 401，控制台不会被登出），恢复后照常。
- **不再读取的环境变量：** `SUB2API_JWT_SECRET`、`SUB2API_ACCESS_TOKEN_TTL`、`SUB2API_REFRESH_TOKEN_TTL`、`SUB2API_SESSION_ISSUE`。留着无害（网关也不再把它们传给核心），可以在发布后从 `.env` 和网关配置里删掉。会话时长由 `SUB2API_SESSION_IDLE_TTL`（默认 168h）和 `SUB2API_SESSION_MAX_TTL`（默认 720h）决定。

## 发布步骤

**先停掉全部核心节点，再启动新版本。** 上一版节点读写被删的三张表，新旧节点混跑时旧节点的登录、换发和二次验证会报错。

- **网关托管（线上）**：照常建升级计划。`primary-first-v1` 先停掉所有从节点的核心，主节点停机后才迁移并启动新版本（`deploy/gateway/README.md`），本身满足“先全停”。
- **非托管（`deploy/single`、直接运行核心的多节点部署）**：停掉每个节点，确认没有上一版核心在跑，再启动新版本；第一个节点启动时执行迁移 0101。

发布前**做一次数据库备份**，这是唯一的回退途径。

发布后核对：

```sql
SELECT id FROM schema_migrations WHERE id = '0101_drop_jwt_sessions.sql';                          -- 一行
SELECT to_regclass('refresh_tokens'), to_regclass('login_sessions'), to_regclass('auth_flows');   -- 都是 NULL
```

用超管登录一次，`POST /api/v1/auth/login` 返回的 `access_token` 以 `s2s_` 开头。

## 回退

网关拒绝跨 schema 回退（`sub2api-gateway rollback` 和建计划都会拒绝），托管核心见到不认识的迁移也拒绝启动。回到上一版的唯一办法是**从发布前的备份恢复数据库**：

1. 停掉所有核心节点。
2. 从发布前的备份恢复数据库。
3. 恢复上一版的环境变量（至少 `SUB2API_JWT_SECRET`，必须是原来的值）。
4. 启动上一版核心。备份之后在新版本里发生的写入全部丢失；Valkey 里的 `s2a:sess:*`、`s2a:usess:*`、`s2a:sid:*`、`s2a:flow:*` 上一版不读，留着无害，到期自动消失。所有人再重新登录一次。

线上出问题首选**修复前进**（下一个核心版本，新迁移接在 0101 之后）。

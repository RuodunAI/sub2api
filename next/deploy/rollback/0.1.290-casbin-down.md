# 0.1.290 Casbin 权限存储：自检、核对与回退

> 0.1.290 是一个发布单元（0099–0101），从线上 0.1.288 直接升级，0.1.289 没有单独发布。升级顺序、备份和回退的完整步骤见 `0.1.290-release.md`；本文只讲 0100 自己的部分。

核心 0.1.290 的迁移 `0100_casbin_rule.sql`（设计见 CONTRACTS §99）把旧角色表 `role_permissions`、`role_permission_scopes`、`user_roles` 与 `roles.superuser` 的授予转换成 `casbin_rule` 的行，然后**删除这三张表**、0097 的 `user_roles_one_superuser()` 和 `permissions.sensitive`（0099 已按它回填 `risk`）；此后所有授予与角色指派只写 `casbin_rule`。

**这个迁移是单向的。** 没有反向脚本，也没有运行时开关：0.1.288 及更早的核心读写的是已经删掉的表，不能在这个库上运行。回到 0.1.288 的唯一办法是**从升级前的备份恢复**，升级之后的所有写入（不只是授予）都会丢失。`0.1.290-casbin-down.sql` 只会报错说明这一点，什么也不改。

## 发布：必须停服

1. **停服与备份**按 `0.1.290-release.md` 第三节：迁移期间不能有任何旧版本核心在写角色表，迁移之后旧核心也不能再启动。托管部署在建升级计划之前备份，计划按 `primary-first-v1` 先停从节点，主节点最后进入维护、停机后迁移；非托管部署先停掉全部节点（顺序不限），再备份。
2. 备份是唯一的回退途径，确认它可读。
3. 升级前自检（可选，迁移本身也会检查并报错停止）：

   ```sql
   SELECT key FROM roles WHERE key = '_self';                       -- 应无行：保留 key
   SELECT key FROM permissions WHERE key = '*';                     -- 应无行：保留 key
   SELECT key FROM roles WHERE superuser AND key <> 'super_admin';  -- 应无行：只有 super_admin 能是超管角色
   SELECT DISTINCT ur.user_id FROM user_roles ur JOIN roles r ON r.id = ur.role_id
   WHERE r.superuser;                                               -- 至多 1 行：超管持有者（已软删除的也算）
   ```

   有行时按迁移报错里的 HINT 改名或删除，再升级；超管持有者多于一个时，在建计划之前用线上运行的 0.1.288 执行 `sub2api admin recover-superadmin --email <要保留的用户>` 保留一个（托管节点上的完整命令见 `0.1.290-release.md` 第二节）。
4. **0.1.290 的主节点（非托管部署：第一个启动的节点）执行迁移**：0100 是一个事务，失败不留半截，`lock_timeout` 10 秒；成功后其余节点才启动。
5. **核对**：

   ```sql
   SELECT id FROM schema_migrations WHERE id = '0100_casbin_rule.sql';                -- 1 行
   SELECT to_regclass('role_permissions'), to_regclass('role_permission_scopes'),
          to_regclass('user_roles'), to_regprocedure('user_roles_one_superuser()');   -- 全部为空
   SELECT ptype, count(*) FROM casbin_rule GROUP BY ptype;                            -- p 行与 g 行的数量
   SELECT v0 FROM casbin_rule WHERE ptype = 'p' AND v1 = '*';                         -- 只有 r:super_admin
   SELECT count(*) FROM casbin_rule WHERE ptype = 'g' AND v1 = 'r:super_admin';       -- 1
   ```

   转换出的行都来自旧表与 `roles`、`permissions` 的连接（旧表对用户、角色、权限有外键），不会指向不存在的行；之后的删除路径各自清理（CONTRACTS §99.1），测试在每个数据库测试结束时核对。

   行数可以和备份里的旧表对照：p 行 = `role_permissions` 行 + `role_permission_scopes` 行 + 超管角色数（两种方式都持有的同一授予只算一次），g 行 = `user_roles` 行。再用超管和一个普通用户登录控制台，确认菜单与权限正常。

升级若停在 0100（有多个超管持有者），按 HINT 用 0.1.288 的 `sub2api admin recover-superadmin --email <要保留的用户>` 保留一个（其余的变成管理员），再继续升级。此时库还在 0100 之前，0.1.290 的 `sub2api admin` 只在迁移完成的库上执行，发现 schema 不对会拒绝。0.1.288 的二进制在托管节点上的位置、需要的环境变量和完整命令见 `0.1.290-release.md` 第四节“停服时执行 0.1.288 的 `sub2api admin`”。

## 回退：从备份恢复到 0.1.288

完整步骤见 `0.1.290-release.md` 第五节，与 0100 有关的是：

1. 停掉所有 0.1.290 节点。
2. 用升级前的备份恢复整个数据库（`pg_restore --clean --if-exists -d "$DATABASE_URL" before-0.1.290.dump`，或回滚平台快照）。
3. Valkey 不用清理：0.1.290 的节点把授权策略放在自己的内存里（CONTRACTS §99.4），Valkey 里没有授权的键。
4. 启动 0.1.288 核心，核对：

   ```sql
   SELECT count(*) FROM schema_migrations WHERE id >= '0099';   -- 0
   SELECT to_regclass('casbin_rule');                            -- 空
   SELECT to_regclass('user_roles');                             -- user_roles
   ```

托管部署（经网关）本来就不允许跨 schema 回退（网关拒绝建计划、主节点启动目标核心与 `sub2api-gateway rollback`），只能按上面的步骤从备份恢复，或修复前进（下一个核心版本，新迁移接在 0100 之后）。

## 开发库

应用过任何发布前构建的 0099、0100 或 0101 的库（开发库、预发库）与发布版的校验和或 schema 不同，0.1.290 拒绝启动。这类库重建，或恢复到 0098 的备份后再升级；不要手改 `schema_migrations` 的校验和。线上从 0.1.288 升级不受影响。

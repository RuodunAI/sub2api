# 0.1.290 Casbin 策略投影的回滚

> 版本号 0.1.290 是候选值（权限判断接入 Casbin 的阶段 S1 预计随它发布），发布时改成真实版本（文件名、脚本注释与本文一起改）。

核心 0.1.290 只有一个新迁移 `0100_casbin_rule.sql`（设计见 CONTRACTS §99，Mode P）：新建 `casbin_rule`（gorm-adapter 列布局）与两个视图 `authz_casbin_expected`、`authz_casbin_drift`，在 `role_permissions`、`role_permission_scopes`、`user_roles`、`roles`、`permissions`、`users` 上挂触发器，在同一事务里把旧角色表投影进 `casbin_rule`；再加上这些表与 `casbin_rule` 的 TRUNCATE 语句级触发器（截断后按视图重建投影），以及修正函数 `authz_casbin_repair()`。迁移按视图回填，写了东西就推进 authz 版本。回滚目标是上一版本核心 0.1.289（schema 0099）。

**迁移只做加法**：旧角色表仍是写入的真相，一行没有改写，回滚不丢任何数据。0.1.289 核心不读 `casbin_rule`，触发器在它的写入上照常工作，没有害处；所以即使不跑反向脚本，旧核心的读写也是对的。

## 首选：切开关，不回退 schema

权限判断出问题时，把系统设置 `authz.engine` 改成 `legacy`（运行时生效，不需要发版；应急时也可以给每个节点设环境变量 `SUP2API_AUTHZ_ENGINE=legacy` 再重启）。旧加载器重新说了算，`casbin_rule` 与触发器留着不碍事。修好之后再切回 `shadow`。

## 托管部署（线上网关）不能回到 0.1.289

与 0.1.286、0.1.289 相同（见 `0.1.286-authz-down.md`）：网关不允许跨 schema 回退（`deploy/gateway/README.md`），建计划、主节点启动目标核心、`sub2api-gateway rollback` 三处都会拒绝；托管核心见到库里有它不认识的迁移会拒绝启动（`app/managed_checks.go` `appliedPrefix`）。线上只能**切开关**（上一节）或**修复前进**（下一个核心版本，新迁移接在 0100 之后）；确实要回到 0.1.289 只能从数据库备份恢复。下面的步骤只适用于非托管部署（测试环境、生产备份验证环境、不经网关直接运行核心的部署）。

## 先判断要不要跑反向脚本

```sql
SELECT id FROM schema_migrations WHERE id = '0100_casbin_rule.sql';
```

没有这一行说明迁移没有提交，库还是 0.1.289 的形态，不要跑反向脚本。

## 回滚步骤

1. **停掉所有 0.1.290 核心**。0.1.289 核心要在脚本跑完后再启动（先启动了也不要紧：迁移只做了加法，停掉它再跑脚本即可）。
2. **跑反向脚本**（数据库属主，一个事务，失败不留半截）：

   ```sh
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.290-casbin-down.sql
   ```

   脚本先检查 `0100_casbin_rule.sql` 已应用、之后没有更新的迁移，否则直接报错退出、什么也不改。然后删除 13 个触发器（6 个行级 `casbin_sync`、7 个 `casbin_sync_truncate`）、10 个函数、2 个视图和 `casbin_rule`，删除 `schema_migrations` 里的那一行，推进 authz 版本。
3. **启动 0.1.289 核心**。库里的迁移正好是它的 0001–0099，不再跑迁移。
4. **核对**：

   ```sql
   SELECT count(*) FROM schema_migrations WHERE id >= '0100';                       -- 0
   SELECT to_regclass('casbin_rule'), to_regclass('authz_casbin_drift');            -- 都是空
   SELECT tgname FROM pg_trigger WHERE tgname LIKE 'casbin_sync%';                  -- 无行
   SELECT proname FROM pg_proc WHERE proname LIKE 'authz_casbin_%';                 -- 无行
   ```

## 再次升级

直接再发 0.1.290。迁移重新建表、视图与触发器，按旧角色表回填（回滚期间旧核心的写入都在旧表里，回填后投影是准确的），漂移为 0。

`TestCasbinRuleDown`（`server/internal/migrations`）在测试库上验证：迁移到 0100 后写入授予，执行本脚本后表结构与只迁移到 0099 的库一致，授予不变，版本推进一次；再执行一次报 `nothing to roll back`；再升级后投影与回滚前相同。`TestAuthzHardeningRollback`、`TestPluginPermissionMetaRollback` 先跑本脚本再跑 0.1.289、0.1.286 的反向脚本。

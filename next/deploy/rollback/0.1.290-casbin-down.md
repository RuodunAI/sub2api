# 0.1.290 Casbin 权限存储：发布与回退

> 版本号 0.1.290 是候选值，发布时改成真实版本（文件名、脚本注释与本文一起改）。

核心 0.1.290 的迁移 `0100_casbin_rule.sql`（设计见 CONTRACTS §99）把旧角色表 `role_permissions`、`role_permission_scopes`、`user_roles` 与 `roles.superuser` 的授予转换成 `casbin_rule` 的行，然后**删除这三张表**和 0097 的 `user_roles_one_superuser()`；此后所有授予与角色指派只写 `casbin_rule`。

**这个迁移是单向的。** 没有反向脚本，也没有运行时开关：0.1.289 及更早的核心读写的是已经删掉的表，不能在这个库上运行。回到 0.1.289 的唯一办法是**从升级前的备份恢复**，升级之后的所有写入（不只是授予）都会丢失。`0.1.290-casbin-down.sql` 只会报错说明这一点，什么也不改。

## 发布：必须停服

1. **停掉所有节点，主节点先停**（托管部署：先停主节点上的核心，再停其余节点；`deploy/single`：`docker compose stop`）。迁移期间不能有任何旧版本核心在写角色表，迁移之后旧核心也不能再启动。
2. **备份数据库**（`pg_dump -Fc "$DATABASE_URL" > before-0.1.290.dump`，或平台快照），确认备份可读。这是唯一的回退途径。
3. 升级前自检（可选，迁移本身也会检查并报错停止）：

   ```sql
   SELECT key FROM roles WHERE key = '_self';                       -- 应无行：保留 key
   SELECT key FROM permissions WHERE key = '*';                     -- 应无行：保留 key
   SELECT key FROM roles WHERE superuser AND key <> 'super_admin';  -- 应无行：只有 super_admin 能是超管角色
   SELECT DISTINCT ur.user_id FROM user_roles ur JOIN roles r ON r.id = ur.role_id
   WHERE r.superuser;                                               -- 至多 1 行：超管持有者（已软删除的也算）
   ```

   有行时按迁移报错里的 HINT 改名或删除，再升级；超管持有者多于一个时用 `sub2api admin recover-superadmin --email <要保留的用户>` 保留一个（见下文“升级若停在”一段）。
4. **启动 0.1.290 的主节点**，由它执行迁移（一个事务，失败不留半截，`lock_timeout` 10 秒）；成功后再启动其余节点。
5. **核对**：

   ```sql
   SELECT id FROM schema_migrations WHERE id = '0100_casbin_rule.sql';                -- 1 行
   SELECT to_regclass('role_permissions'), to_regclass('role_permission_scopes'),
          to_regclass('user_roles'), to_regprocedure('user_roles_one_superuser()');   -- 全部为空
   SELECT ptype, count(*) FROM casbin_rule GROUP BY ptype;                            -- p 行与 g 行的数量
   SELECT v0 FROM casbin_rule WHERE ptype = 'p' AND v1 = '*';                         -- 只有 r:super_admin
   SELECT count(*) FROM casbin_rule WHERE ptype = 'g' AND v1 = 'r:super_admin';       -- 1
   ```

   转换出的行都来自旧表与 `roles`、`permissions` 的连接（旧表对用户、角色、权限有外键），不会指向不存在的行；之后的删除路径各自清理（CONTRACTS §99.1），测试在每个数据库测试结束时核对。

   行数可以和备份里的旧表对照：p 行 = `role_permissions` 行 + `role_permission_scopes` 行 + 超管角色数（两种方式都持有的同一授予只算一次），g 行 = `user_roles` 行。再用超管和一个普通用户登录控制台，确认菜单与权限正常。

升级若停在 0097（库里没有或有多个超管）或 0100（有多个超管持有者），按报错用 0.1.290 的 `sub2api admin recover-superadmin --email <要保留的用户>` 处理。此时库还在 0100 之前，命令只做移交：目标必须是启用的用户，不能带 `--reset-password`、`--reset-2fa`；启动核心完成迁移后，需要的话再带上它们跑一次。

## 回退：从备份恢复

1. 停掉所有 0.1.290 节点。
2. 用发布第 2 步的备份恢复数据库（`pg_restore --clean --if-exists -d "$DATABASE_URL" before-0.1.290.dump`，或回滚平台快照）。
3. **清掉 Valkey 里的角色缓存**（恢复会让 authz 版本回退，恢复前写下、还在 TTL 内的条目可能被当成新状态命中，CONTRACTS §99.4）：

   ```sh
   valkey-cli -u "$REDIS_URL" --scan --pattern 'authz:c:ur:*' | xargs -r -n 500 valkey-cli -u "$REDIS_URL" UNLINK
   ```

   （`redis-cli` 同样用法；集群模式对每个主节点各执行一次。）
4. 启动 0.1.289 核心，核对：

   ```sql
   SELECT count(*) FROM schema_migrations WHERE id >= '0100';   -- 0
   SELECT to_regclass('casbin_rule');                            -- 空
   SELECT to_regclass('user_roles');                             -- user_roles
   ```

托管部署（经网关）本来就不允许跨 schema 回退（网关拒绝建计划、主节点启动目标核心与 `sub2api-gateway rollback`），只能按上面的步骤从备份恢复，或修复前进（下一个核心版本，新迁移接在 0100 之后）。

## 开发库

应用过未发布的 Mode P 版 `0100_casbin_rule.sql`（建了触发器和视图、保留旧表的那一版）的开发库，文件校验和与现在的不同，新核心会拒绝启动。重建开发库，或恢复到 0099 的备份后再升级。0099 在 develop 上有过两种内容（`b5b2fb564` 的第一版，`1ef272c02` 起在 `permissions.status` 的 COMMENT 里加了 staged），两种校验和核心都接受（`store.CoreTracker` 的 `supersededCoreMigrations`，`TestSupersededCoreMigrationIsAccepted`），0100 再写一次那条 COMMENT；0099 的文件内容不再改动。

## 测试

`server/internal/migrations` 的 `TestCasbinRuleMigration`（转换结果、旧表与函数已删、版本只升一次、重跑不变、一人超管索引）、`TestCasbinRuleReservedKeys`（保留 key 与行形状约束，迁移前已有的保留 key 停止升级）、`TestCasbinRuleSeveralSuperAdmins`（多个超管持有者停止升级，HINT 指向 CLI）、`TestCasbinRuleOneWay`（本目录的 `.sql` 报错且不改库）、`TestCasbinRuleOneSuperuserConcurrent`；`server/internal/iam` 的 `TestRecoverSuperAdminBeforeCasbinRule`（停在 0097 时的 CLI）。`TestAuthzHardeningRollback`、`TestPluginPermissionMetaRollback` 只升级到 0099 再跑 0.1.289、0.1.286 的反向脚本。

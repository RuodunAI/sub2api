# 0.1.290：从 0.1.288 升级与回退

0.1.290 是一个发布单元：插件权限声明（迁移 0099）、Casbin 权限存储（0100）、Valkey 控制台会话（0101）和 GORM 数据访问一起发布。开发时插件权限这部分曾按 0.1.289 规划，**0.1.289 没有单独发布**。线上是 0.1.288，schema 停在 0098（契约 `1f73f300…9d4f`），升级时 0099、0100、0101 依次执行，每个文件一个事务。

**这次发布是单向的。** 0100 删掉旧角色表，0101 删掉 JWT 会话表，0.1.288 不能在升级后的库上运行。回退目标是 0.1.288，唯一途径是**从升级前（从 0.1.288 升级之前）做的数据库备份恢复**，备份之后的写入全部丢失。没有反向脚本，也没有运行时开关。

用户看到的影响：所有人重新登录；权限不变（同样的角色、授予得到同样的结果）；停服时间与 0.1.286 同一量级（三个迁移在线上规模下都是秒级），另加插件准备的时间。

各部分的细节：

- 0100 的升级前自检、迁移后核对、停在 0097 或 0100 时的处理：`0.1.290-casbin-down.md`。
- 会话、`SUB2API_JWT_SECRET` 和 Valkey：`0.1.290-session-down.md`。
- 用户可见的变化与插件版本：仓库根目录 `CHANGELOG.md` 的 0.1.290 一节。

## 一、在生产副本上演练

发布前在一份线上备份上把整个升级跑一遍，确认每个用户的有效权限不变，并记下迁移耗时。

1. 把最近的线上备份恢复到一个**不能访问外网**的环境，配一个独立的 Valkey。演练核心会启动插件和后台任务，能出网时会用线上的账号凭证刷新 OAuth 令牌、调用上游，影响线上账号。
2. 导出升级前的有效权限，并跑 `0.1.290-casbin-down.md` 第 3 步的自检 SQL：

   ```sh
   psql "$DATABASE_URL" -X -q -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.290-effective-permissions.sql > before.tsv
   ```

   每行是“用户 id、权限 key、范围”，只列核心让其生效的部分：启用、未删除的用户，状态为 active 的权限，超管一行 `<id> * *`。脚本只读，老 schema（角色表）和新 schema（`casbin_rule`）都能读。
3. 不经网关启动 0.1.290 核心（配置照 `deploy/single`），连这份副本。日志 `migrations applied` 列出 0099、0100、0101。记下从启动到这一行的耗时；迁移期间另开一个会话查锁等待：

   ```sql
   SELECT pid, wait_event_type, wait_event, now() - query_start AS waited, left(query, 80)
   FROM pg_stat_activity WHERE wait_event_type = 'Lock';
   ```

4. 等控制台的插件列表显示内置插件已升到新版本，再导出一次并比较：

   ```sh
   psql "$DATABASE_URL" -X -q -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.290-effective-permissions.sql > after.tsv
   diff before.tsv after.tsv && echo same
   ```

   **结果必须完全相同。** 本次没有新增或删除核心权限 key；内置插件新版本声明的权限 key 与线上版本相同，已有的 key 不会重新按默认值授予。有任何差异就停下来查清原因，再决定是否发布。
5. 跑 `0.1.290-casbin-down.md` 第 5 步和 `0.1.290-session-down.md` 的核对 SQL。分别用超管和一个普通用户登录控制台，确认菜单和权限正常，登录得到的令牌以 `s2s_` 开头。

`TestEffectivePermissionsScript`（`server/internal/migrations`）在测试库上验证这个脚本：同一份数据在 0100 前后导出的结果相同。

## 二、发布前

- `.env` 里保留 `SUB2API_JWT_SECRET`。0.1.290 不读它，但回退到 0.1.288 时要用原值（`0.1.290-session-down.md`）。
- 记下插件版本，回退后用来核对：`SELECT key, active_version FROM plugins ORDER BY key;`
- 内置插件包：ccgateway 0.1.133 和 mailer 0.1.2 版本没变，只是用新 SDK 重新编译，发布时沿用线上包的字节。同一个版本号、内容不同的包会被内置同步跳过（只记一条 WARN），所以重新打的包不会生效。

## 三、备份与发布

### 网关托管（线上）

1. 导入 0.1.290 清单，`--preflight-only` 确认选中 `primary-first-v1`，并且没有 blocker。
2. **备份整个数据库**：`pg_dump -Fc "$DATABASE_URL" > before-0.1.290.dump`，或做平台快照。整个库包括网关的 `updater` 表和插件的 schema。确认备份可读，这是唯一的回退途径。

   备份必须在建计划之前做：计划建好后，从停从节点到主节点迁移会一直执行下去，中间不停下来等人。备份之后、主节点进入维护之前的写入（计费、使用记录、控制台操作），在回退时会丢失。想让这段尽量短，可以先关掉入口流量（例如 new-api 渠道），再做备份，备份完马上建计划。
3. 建计划。网关按下面的顺序执行，不需要人工介入：
   1. 所有节点下载并校验发布包（`prepare`）。
   2. 每个从节点把入口转发到主节点（`redirect`），然后停掉核心（`stop`）。这时主节点的旧核心承接全部流量。
   3. 主节点进入维护（`maintenance`），从这一步起整个集群不可用；然后停掉旧核心（`stop`）。
   4. 主节点带着迁移许可启动 0.1.290（`start-primary`），依次执行 0099、0100、0101，然后准入并恢复本地服务（`admit`、`local`）。停服到这里结束。
   5. 每个从节点启动 0.1.290，准入后恢复本地服务；在这之前，它一直把请求转发给主节点。

   所有节点都运行新核心之后，内置插件同步开始升级内置插件，每 10 秒重试一次。

### 非托管（`deploy/single`、不经网关直接运行核心的多节点部署）

1. 停掉每个节点，顺序不限。确认没有 0.1.288 核心还在运行。
2. 按上面的方式备份整个数据库。
3. 启动一个节点，由它执行三个迁移。成功后再启动其余节点。

## 四、升级停在中途

每个迁移文件单独一个事务。例如 0100 因为库里有多个超管被拒时，0099 已经提交，0100 什么也没写。这时：

- 0.1.288 核心不接受这个库：托管核心报 `database includes migrations unknown to this core`。新核心也不会在没迁移完的库上提供服务。托管部署的计划会暂停，主节点保持维护状态，从节点不会自己启动。
- 修复数据：报错和 HINT 会说明怎样改，常见情况见 `0.1.290-casbin-down.md` 的“升级若停在”一段。修复时用发布包里的 0.1.290 `sub2api` 二进制，例如 `sub2api admin recover-superadmin --email …`。`lock_timeout`（10 秒）超时的情况，直接重试即可。
- 继续升级：托管部署执行 `sub2api-gateway resume -id <计划 id>`，`start-primary` 用同一个迁移许可从 0100 接着执行；非托管部署重新启动那个节点。`TestManagedUpgradeFromProductionResumesWithTheSamePermit`（`server/internal/app`）验证了这条路径。
- 如果不想修复前进，就按第五节从备份恢复。

## 五、回退：从备份恢复到 0.1.288

网关不允许跨 schema 回退：升级计划、主节点启动目标核心、`sub2api-gateway rollback` 三处都会拒绝。所以只能从备份恢复。

1. 停掉所有核心。托管部署停掉所有网关节点（`docker compose stop`）；非托管部署停掉所有节点。
2. 用第三节的备份恢复整个数据库：`pg_restore --clean --if-exists -d "$DATABASE_URL" before-0.1.290.dump`，或回滚平台快照。
3. 清掉 Valkey 里的权限角色缓存（恢复后 authz 版本会回退，旧条目可能被当成新状态命中，见 CONTRACTS §99.4）：

   ```sh
   valkey-cli -u "$REDIS_URL" --scan --pattern 'authz:c:ur:*' | xargs -r -n 500 valkey-cli -u "$REDIS_URL" UNLINK
   ```

   `redis-cli` 用法相同；集群模式下对每个主节点各执行一次。
4. 确认 `.env` 里的 `SUB2API_JWT_SECRET` 是原来的值。
5. 启动。托管部署启动网关节点：恢复出来的 `updater` 表里没有这次的计划，基线仍是 0.1.288，节点按基线启动 0.1.288 核心。非托管部署启动 0.1.288 核心。插件版本随备份回到原样，内置包也随 0.1.288 回到原来的集合，不需要另外降级插件。
6. 核对：

   ```sql
   SELECT max(id) FROM schema_migrations;   -- 0098_plugin_staged_grants.sql
   SELECT to_regclass('casbin_rule');        -- 空
   SELECT to_regclass('user_roles');         -- user_roles
   SELECT key, active_version FROM plugins ORDER BY key;   -- 与第二节记下的相同
   ```

   Valkey 里的 `s2a:sess:*`、`s2a:usess:*`、`s2a:sid:*`、`s2a:flow:*` 0.1.288 不读，留着无害，到期后自动消失。所有人需要再重新登录一次。

`0.1.289-plugin-perm-down.sql` 不用于这里，它只适用于停在 0099 的开发库或测试库。

## 开发库和测试环境

- **跑过 develop 上 0.1.289 构建的库**（schema 0099）：0099 与 develop 上的文件逐字节相同，可以直接升级到 0.1.290；0.1.289 写下的已移除、暂存的插件权限和插件范围授予由 0100 原样转换。要回到 0.1.288，用 `0.1.289-plugin-perm-down.md` 的反向脚本。
- **跑过未发布的 Mode P 版 0100 的库**：见 `0.1.290-casbin-down.md` 的“开发库”一节。
- **跑过未发布的会话双模式构建的库**：那一版在 `settings` 里存过签发开关的 `session` 行。0101 会删除这一行，线上库没有这一行，所以这条 DELETE 在线上什么也不删。

## 测试

- `server/internal/app` 的 `TestManagedUpgradeFromProductionResumesWithTheSamePermit`：0098 的库在同一个许可下升级。0100 因为两个超管被拒时 0099 保留，新旧核心都不接受这个库；修复后用同一个许可完成升级，再启动一次什么也不改。这个测试还固定了线上 schema 契约，已发布迁移的字节一旦变化，测试就会失败。
- `server/internal/migrations` 的 `TestEffectivePermissionsScript`，以及 `0.1.290-casbin-down.md`、`0.1.290-session-down.md` 列出的迁移测试。

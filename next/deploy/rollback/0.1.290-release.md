# 0.1.290：从 0.1.288 升级与回退

0.1.290 是一个发布单元：插件权限声明（迁移 0099）、Casbin 权限存储（0100）、Valkey 控制台会话（0101）、删除 CCGateway 与旧版本兼容数据（0102）和 GORM 数据访问一起发布。开发时插件权限这部分曾按 0.1.289 规划，**0.1.289 没有单独发布**。线上是 0.1.288，schema 停在 0098（契约 `1f73f300…9d4f`），升级时 0099、0100、0101、0102 依次执行，每个文件一个事务。

**这次发布是单向的。** 0100 删掉旧角色表，0101 删掉 JWT 会话表，0102 删掉 CCGateway 的表和插件行，0.1.288 不能在升级后的库上运行，也不能与 0.1.290 同时运行。回退目标是 0.1.288，唯一途径是**从升级前（从 0.1.288 升级之前）做的数据库备份恢复**，网关外壳也一起回到 0.1.288 时的版本，备份之后的写入全部丢失。没有反向脚本，也没有运行时开关。

用户看到的影响：所有人重新登录；权限不变（同样的角色、授予得到同样的结果）；停服时间与 0.1.286 同一量级（四个迁移在线上规模下都是秒级），另加插件准备的时间。

各部分的细节：

- 0100 的升级前自检、迁移后核对、停在 0100 时的处理：`0.1.290-casbin-down.md`。
- 会话和 Valkey：`0.1.290-session-down.md`。
- 0102 删除 CCGateway、账号生命周期契约与只为旧核心保留的数据：第二节的核对 SQL、第六节的发布后步骤。
- 用户可见的变化与插件版本：仓库根目录 `CHANGELOG.md` 的 0.1.290 一节。

## 一、在生产副本上演练

发布前在一份线上备份上把整个升级跑一遍，确认每个用户的有效权限不变，并记下迁移耗时。

1. 把最近的线上备份恢复到一个**不能访问外网**的环境，配一个独立的 Valkey。演练核心会启动插件和后台任务，能出网时会用线上的账号凭证刷新 OAuth 令牌、调用上游，影响线上账号。
2. 导出升级前的有效权限，并跑 `0.1.290-casbin-down.md` 第 3 步的自检 SQL：

   ```sh
   psql "$DATABASE_URL" -X -q -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.290-effective-permissions.sql > before.tsv
   ```

   每行是“用户 id、权限 key、范围”，只列核心让其生效的部分：启用、未删除的用户，状态为 active 的权限，超管一行 `<id> * *`。脚本只读，老 schema（角色表）和新 schema（`casbin_rule`）都能读。
3. 不经网关启动 0.1.290 核心（配置照 `deploy/single`），连这份副本。日志 `migrations applied` 列出 0099、0100、0101、0102。记下从启动到这一行的耗时；迁移期间另开一个会话查锁等待：

   ```sql
   SELECT pid, wait_event_type, wait_event, now() - query_start AS waited, left(query, 80)
   FROM pg_stat_activity WHERE wait_event_type = 'Lock';
   ```

4. 等控制台的插件列表显示内置插件已升到新版本，再导出一次并比较：

   ```sh
   psql "$DATABASE_URL" -X -q -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.290-effective-permissions.sql > after.tsv
   diff before.tsv after.tsv && echo same
   ```

   **结果必须完全相同。** 本次没有新增或删除核心权限 key；内置插件新版本声明的权限 key 与线上版本相同，已有的 key 不会重新按默认值授予。有任何差异就停下来查清原因，再决定是否发布。
5. 跑 `0.1.290-casbin-down.md` 第 5 步和 `0.1.290-session-down.md` 的核对 SQL。分别用超管和一个普通用户登录控制台，确认菜单和权限正常，登录得到的令牌以 `s2s_` 开头。

`TestEffectivePermissionsScript`（`server/internal/migrations`）在测试库上验证这个脚本：同一份数据在 0100 前后导出的结果相同。

## 二、发布前

- 把每个节点的 compose 文件和 `.env` 复制一份，托管部署另记下网关外壳的镜像版本，和数据库备份放在一起：回退时一起恢复（本次的 compose 不再传 `SUB2API_JWT_SECRET`，0.1.288 核心启动要用 `.env` 里它原来的值）。
- 确认各节点 `.env` 的 `DATABASE_URL` 没有 `pool_*` 参数（0.1.290 不再从 DSN 读连接池参数，带了的话核心、网关外壳和插件启动即失败，报错只列参数名）；连接数用 `SUB2API_PG_MAX_CONNS`（核心）和 `SUB2API_GATEWAY_POOL_MAX_CONNS`（网关）设置。
- 记下插件版本，回退后用来核对：`SELECT key, active_version FROM plugins ORDER BY key;`
- 在线上库跑 `0.1.290-casbin-down.md` 第 3 步的自检 SQL（只读）。超管持有者多于一个时，在建计划之前用线上正在运行的 0.1.288 处理掉，升级就不会停在 0100：托管部署 `docker exec <网关容器> /var/lib/sub2api/current/bin/sub2api admin recover-superadmin --email <要保留的用户>`（建计划之前每个节点的 `current` 都是 0.1.288；环境变量见第四节）。
- 非托管部署给 0.1.288 的镜像另打一个标签（`docker tag sup2api:latest sup2api:0.1.288`）：`deploy/single` 构建 0.1.290 时会覆盖 `sup2api:latest`，停在中途和回退时要用它。
- 内置插件全部升了版本（见 CHANGELOG“插件版本”），都要求核心 ≥0.1.290，随核心一起发布；内置同步按新版本号上传，不会出现同版本号不同内容的跳过。ccgateway 不再内置。
- 在线上库（或生产副本）跑下面的只读 SQL，记下 0102 会删除和保留的行数，放进发布记录。2026-11-15 的生产副本：ccgateway 插件行 enabled、builtin、0.1.133，没有 `plg_ccgateway` schema；`ccgateway_runtimes` 104 行，特性策略、请求日志、`provider_resources`、`provider_fallback_credits` 各约 1 行，`provider_resource_contexts` 0 行；`plugin_key = 'ccgateway'` 的账号 104 个，全部已软删除。

  ```sql
  -- 0102 deletes (counts before the upgrade)
  SELECT key, status, builtin, active_version FROM plugins WHERE key = 'ccgateway';
  SELECT (SELECT count(*) FROM plugin_versions WHERE plugin_key = 'ccgateway') AS versions,
         (SELECT count(*) FROM permissions WHERE plugin_key = 'ccgateway') AS permissions,
         (SELECT count(*) FROM role_permissions rp JOIN permissions p ON p.id = rp.permission_id

           OR plugin_key = 'ccgateway') AS tasks,
         (SELECT count(*) FROM settings WHERE key = 'ccgateway_remote') AS settings,
         (SELECT count(*) FROM accounts WHERE rate_limit_tier IS NOT NULL) AS rate_limit_tiers,
         to_regnamespace('plg_ccgateway') AS schema;
  SELECT 'ccgateway_runtimes' AS "table", count(*) FROM ccgateway_runtimes
  UNION ALL SELECT 'ccgateway_account_feature_policies', count(*) FROM ccgateway_account_feature_policies
  UNION ALL SELECT 'ccgateway_account_request_logs', count(*) FROM ccgateway_account_request_logs
  UNION ALL SELECT 'provider_resources', count(*) FROM provider_resources
  UNION ALL SELECT 'provider_resource_contexts', count(*) FROM provider_resource_contexts
  UNION ALL SELECT 'provider_skill_versions', count(*) FROM provider_skill_versions
  UNION ALL SELECT 'provider_fallback_credits', count(*) FROM provider_fallback_credits
  UNION ALL SELECT 'provider_diagnostic_messages', count(*) FROM provider_diagnostic_messages
  UNION ALL SELECT 'provider_helper_attempts', count(*) FROM provider_helper_attempts
  UNION ALL SELECT 'provider_helper_records', count(*) FROM provider_helper_records
  UNION ALL SELECT 'provider_helper_usage_outbox', count(*) FROM provider_helper_usage_outbox
  UNION ALL SELECT 'provider_helper_usage_receipts', count(*) FROM provider_helper_usage_receipts;

         (SELECT value FROM settings WHERE key = 'scheduling') AS scheduling;

  ```

  0102 删除第一、二、三个查询数到的全部内容（插件行连同它的版本、宿主权限授予、事件游标与死信、任务运行、发布记录、节点、卸载屏障、粘性规则；账号生命周期的两张表、两个定时任务），以及 `accounts.status_changed_at`、`accounts.rate_limit_tier`、`accounts.subscription_type`、`accounts.auto_models` 四列；第四个查询：删除 `async_tasks.legacy_imported` 列，`scheduling` 行带 `mode` 时删掉这个键（`mode` 不是 `traffic` 且 `limit_load` 不是 true 时，`metric` 改为 `sessions`、`model_limits` 改为 false，与 0.1.288 读入时的结果相同），没有行或没有 `mode` 时不动；第五个查询数到的账号与使用记录保留，账号在控制台显示为插件已卸载。插件的执行记录、历史与出口日志也保留。0102 不碰 Valkey：ccgateway 没有用插件 KV，`plugin:kv:ccgateway:*` 正常应为空（`redis-cli --scan --pattern 'plugin:kv:ccgateway:*' | head`），有也只是孤立的键。

## 三、备份与发布

### 网关托管（线上）

1. 导入 0.1.290 清单，`--preflight-only` 确认选中 `primary-first-v1`，并且没有 blocker。
2. **备份整个数据库**：`pg_dump -Fc "$DATABASE_URL" > before-0.1.290.dump`，或做平台快照。整个库包括网关的 `updater` 表和插件的 schema。确认备份可读，这是唯一的回退途径。

   备份必须在建计划之前做：计划建好后，从停从节点到主节点迁移会一直执行下去，中间不停下来等人。备份之后、主节点进入维护之前的写入（计费、使用记录、控制台操作），在回退时会丢失。想让这段尽量短，可以先关掉入口流量（例如 new-api 渠道），再做备份，备份完马上建计划。
3. 建计划。网关按下面的顺序执行，不需要人工介入：
   1. 所有节点下载并校验发布包（`prepare`）。
   2. 每个从节点把入口转发到主节点（`redirect`），然后停掉核心（`stop`）。这时主节点的旧核心承接全部流量。
   3. 主节点进入维护（`maintenance`），从这一步起整个集群不可用；然后停掉旧核心（`stop`）。
   4. 主节点带着迁移许可启动 0.1.290（`start-primary`），依次执行 0099、0100、0101、0102，然后准入并恢复本地服务（`admit`、`local`）。停服到这里结束。
   5. 每个从节点启动 0.1.290，准入后恢复本地服务；在这之前，它一直把请求转发给主节点。

   所有节点都运行新核心之后，内置插件同步开始升级内置插件，每 10 秒重试一次。
4. 计划完成后，再逐个节点换上本次构建的网关外壳（镜像与 compose 模板，`deploy/gateway/README.md`）。升级计划始终在原来的外壳下执行：新外壳不再把 `SUB2API_JWT_SECRET` 传给核心，不能运行 0.1.288。`.env` 里的 `SUB2API_JWT_SECRET` 新外壳不用，留着无害。

### 非托管（`deploy/single`、不经网关直接运行核心的多节点部署）

1. 停掉每个节点，顺序不限。确认没有 0.1.288 核心还在运行。
2. 按上面的方式备份整个数据库。
3. 启动一个节点，由它执行四个迁移。成功后再启动其余节点。

## 四、升级停在中途

每个迁移文件单独一个事务。例如 0100 因为库里有多个超管被拒时，0099 已经提交，0100 什么也没写。这时：

- 托管部署：计划暂停，主节点保持维护状态，从节点不会自己启动。新核心不在没迁移完的库上提供服务，托管的 0.1.288 核心也不接受这个库（报 `database includes migrations unknown to this core`）。
- 非托管部署：新核心启动失败后退出。0.1.288 能在这个库上运行（0099 只加列，旧核心不读新列，0.1.290 也还没有写过任何数据），所以可以先把 0.1.288 启动起来，修复数据后再升级。
- 修复数据：报错和 HINT 会说明怎样改，常见情况见 `0.1.290-casbin-down.md` 的“升级若停在”一段。库这时还没到 0.1.290 的 schema，`sub2api admin` 命令用 0.1.288 的二进制执行（见下文）；0.1.290 的 `sub2api admin` 发现库没有迁移完会拒绝执行。`lock_timeout`（10 秒）超时的情况，直接重试即可。
- 继续升级：托管部署执行 `sub2api-gateway resume -id <计划 id>`，`start-primary` 用同一个迁移许可从 0100 接着执行；非托管部署停掉所有节点，再启动一个 0.1.290 节点。`TestManagedUpgradeFromProductionResumesWithTheSamePermit`（`server/internal/app`）验证了这条路径。
- 如果不想修复前进，就按第五节从备份恢复。

### 停服时执行 0.1.288 的 `sub2api admin`

0.1.288 的 CLI 不检查 schema、不跑迁移、不连 Redis，在停在 0099 的库上可用。它启动时照常读配置（0.1.288 的 `config.Load`），要求四个环境变量：`DATABASE_URL`、`REDIS_URL`（非空即可）、`SUB2API_MASTER_KEY`（base64 的 32 字节）、`SUB2API_JWT_SECRET`（至少 32 字节）。

**托管部署。** 网关镜像里没有核心，0.1.288 的核心在网关状态卷的发布目录 `/var/lib/sub2api/releases/<发布包摘要>/bin/sub2api`。主节点在 `start-primary` 时已经把 `current` 指向 0.1.290、`previous` 指向 0.1.288；从节点的 `current` 仍是 0.1.288。按版本找最稳妥：

```sh
docker exec <网关容器> sh -c 'for d in /var/lib/sub2api/releases/*/; do echo "$d $("${d}bin/sub2api" version)"; done'
```

`<网关容器>` 是任一节点的网关容器（ovh 主节点是 `sup2api-1`；示例 `deploy/gateway/compose.yml` 用 `docker compose exec node-a …`）。计划在原来的外壳和 compose 下执行（第三节第 4 步），那份 compose 从 `.env` 给容器设了上面四个变量，`docker exec` 的进程继承容器的环境。先确认它们都在，再执行：

```sh
docker exec <网关容器> sh -c 'for v in DATABASE_URL REDIS_URL SUB2API_MASTER_KEY SUB2API_JWT_SECRET; do [ -n "$(printenv $v)" ] && echo "$v ok" || echo "$v missing"; done'
docker exec <网关容器> /var/lib/sub2api/releases/<0.1.288 的摘要>/bin/sub2api admin recover-superadmin --email <要保留的用户>
```

有变量缺失（例如容器已经按本次的 compose 重建，没有 `SUB2API_JWT_SECRET`）时，用第二节备份的 `.env` 里的原值补上：`docker exec -e SUB2API_JWT_SECRET='<原值>' <网关容器> …`。

**非托管部署（`deploy/single`）。** 用第二节备份的 compose 与 `.env`、0.1.288 的镜像（`docker tag sup2api:0.1.288 sup2api:latest`）启动 0.1.288，再在它的容器里执行（镜像的 `sub2api` 在 `PATH` 里，compose 已设好四个变量）：

```sh
docker compose exec app sub2api admin recover-superadmin --email <要保留的用户>
```

## 五、回退：从备份恢复到 0.1.288

网关不允许跨 schema 回退：升级计划、主节点启动目标核心、`sub2api-gateway rollback` 三处都会拒绝。所以只能从备份恢复。

1. 停掉所有核心。托管部署停掉所有网关节点（`docker compose stop`）；非托管部署停掉所有节点。
2. 用第三节的备份恢复整个数据库：`pg_restore --clean --if-exists -d "$DATABASE_URL" before-0.1.290.dump`，或回滚平台快照。
3. 托管部署把每个节点的网关外壳恢复到第二节记下的版本：外壳镜像、compose 文件和 `.env`（`SUB2API_JWT_SECRET` 是原来的值）。本次的外壳不能运行 0.1.288。非托管部署恢复升级前的 compose 文件和 `.env`。
4. 启动。托管部署启动网关节点：恢复出来的 `updater` 表里没有这次的计划，基线仍是 0.1.288，节点按基线启动 0.1.288 核心。非托管部署启动 0.1.288 核心。插件版本随备份回到原样，内置包也随 0.1.288 回到原来的集合，不需要另外降级插件。
5. 核对：

   ```sql
   SELECT max(id) FROM schema_migrations;   -- 0098_plugin_staged_grants.sql
   SELECT to_regclass('casbin_rule');        -- 空
   SELECT to_regclass('user_roles');         -- user_roles
   SELECT key, active_version FROM plugins ORDER BY key;   -- 与第二节记下的相同
   ```

   Valkey 里的 `s2a:sess:*`、`s2a:usess:*`、`s2a:sid:*`、`s2a:flow:*` 0.1.288 不读，留着无害，到期后自动消失。所有人需要再重新登录一次。

## 六、发布后：停掉 ovh 上的 CCGateway 容器（需要用户同意）

0.1.290 不再连接 CCGateway 的控制器，ovh 上它的容器还在运行：`ccg-controller`、`ccg-guard`、`ccg-state`、`ccg-shared-egress`（另有账号运行环境的容器时一并列出）。它们不影响 0.1.290，所以不在升级计划里，也不自动处理。**只有在用户同意、并且确定不再回退到 0.1.288 之后才做**：回退恢复的 0.1.288 仍把 ccgateway 当作已启用的内置插件，需要这些容器。

1. 核对迁移结果（只读）：

   ```sql
   SELECT to_regclass('ccgateway_runtimes'), to_regclass('provider_resources');   -- 都为空
   SELECT count(*) FROM plugins WHERE key = 'ccgateway';                          -- 0
   SELECT plugin_key FROM plugin_key_retirements WHERE plugin_key = 'ccgateway';  -- ccgateway
   SELECT count(*) FROM accounts WHERE plugin_key = 'ccgateway';                  -- 与第二节记下的相同
   ```

   手里还有 ccgateway 的包（例如 ovh 的 `stage/`）也装不回去：0.1.290 拒绝任何来源、任何签名的 ccgateway 包（403 `plugin_key_reserved`，“removed in core 0.1.290”）。

2. 在 ovh 上列出要处理的容器、它们的卷和镜像，记进发布记录：`docker ps -a --filter name=ccg- --format '{{.Names}} {{.Image}} {{.Status}}'`，对每个容器 `docker inspect --format '{{json .Mounts}}' <名字>`。
3. 停止并删除容器：`docker stop ccg-controller ccg-guard ccg-state ccg-shared-egress`，确认核心与网关照常服务后 `docker rm` 同样四个。
4. 卷（登录状态、请求日志）和镜像先保留；用户确认不再需要之后再 `docker volume rm` / `docker image rm`。`~/sup2api-managed/ccgateway-images/` 下缓存的运行镜像同样等用户确认再删。

## 开发库和测试环境

跑过任何发布前构建的 0099、0100、0101 或 0102 的库（开发库、预发库），迁移的校验和或 schema 与发布版不同，0.1.290 拒绝启动。这类库重建，或恢复到 0098 的备份后再升级；不要手改 `schema_migrations`。
